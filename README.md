# Cohort & Ledger

**A SaaS revenue & retention analytics warehouse — cohort curves, MRR waterfall, NRR, and LTV, computed by a real dimensional warehouse, not a spreadsheet.**

> Subscription businesses live or die by three numbers: how fast MRR grows net of churn, how well each signup cohort retains, and whether revenue retention clears 100%. Getting those numbers right from raw transactional data — trials, upgrades, downgrades, cancellations, reactivations, grandfathered pricing, refunds — is notoriously easy to get subtly wrong. Cohort & Ledger builds the dimensional warehouse to get it right, and proves it with real, measured numbers end to end.

## The problem

Ask five SaaS companies how they calculate Net Revenue Retention and you'll get five different (and sometimes wrong) answers. The usual failure mode is computing these metrics as one-off SQL against the raw `subscriptions` table, which silently mis-handles: a customer who upgrades mid-month, a churned customer who comes back six months later, a plan whose price changed since the customer signed up (grandfathering), or a failed payment that got retried. Each of those is a real edge case that shows up in this project's data, on purpose.

This project builds the warehouse a data/analytics engineer would actually be asked to build: raw OLTP-shaped tables → staged → a proper star schema with SCD Type 2 dimensions → a set of analytics views that compute cohort retention, the MRR waterfall, NRR, and LTV correctly, once, in SQL — so every consumer (this API, a BI tool, an analyst) gets the same right answer instead of five different spreadsheets.

## Data source & methodology

The dataset is **synthetic, not real customer data** — generated by a single fixed-seed script (`data/seed/generate_seed_data.py`, seed `42`) that simulates a B2B SaaS business from **January 2023 through June 2026**: 3,000 customers, 4 pricing tiers (Starter/Growth/Scale/Enterprise, monthly or annual billing), trials with a 30% non-conversion rate, upgrades/downgrades, voluntary and involuntary (failed-payment) churn, an 16% post-churn reactivation rate, refunds, and three rounds of list-price increases that only affect *new* signups — existing subscribers keep their original rate unless they explicitly change plans (grandfathering). Monthly churn hazard is tier-dependent (Starter 4.5%, Enterprise 1.2%) and elevated in the first 3 months of tenure, mirroring the real-world SaaS "leaky bucket" shape.

The generated CSVs are committed to `data/raw/` — the deployed app never depends on re-running the generator or on any live external source, matching the rest of this portfolio series.

| Raw table | Rows | Grain |
|---|---|---|
| `customers` | 3,000 | one row per customer |
| `customers_history` | 3,233 | customer × attribute-version (SCD2 source) |
| `plans_history` | 20 | plan tier × billing interval × price version |
| `subscriptions` | 3,134 | one row per subscription lifecycle (incl. trial-only, reactivations) |
| `plan_changes` | 588 | one row per upgrade/downgrade event |
| `invoices` | 23,759 | one row per billing period |
| `payments` | 24,450 | one row per payment attempt (incl. retries, refunds) |
| `usage_monthly` | 28,889 | customer × subscription × month |

**Data gaps (read this before trusting the numbers):**

- **It's synthetic.** Every number in this README and dashboard is generated, not observed. The *shapes* (churn curves, NRR in the 90-96% range, tier mix) are calibrated to be plausible for a mid-market B2B SaaS company, but they are not empirical.
- **Product usage events are monthly-aggregated**, not event-level (login/feature/API call *counts* per customer per month, not a timestamped event stream), to keep the committed dataset small. A production version would ingest a real event stream (Segment, Amplitude, or first-party) at full granularity.
- **No CAC, no gross margin.** LTV here is revenue-based (ARPU / churn rate), not profit-based — a real LTV:CAC analysis needs marketing spend and COGS data this project doesn't model.
- **Right-censoring is real and shown as such.** Cohorts from the last 12 months haven't lived long enough to reveal their true lifetime value; the LTV view reports their *observed-to-date* revenue plainly rather than extrapolating it into something that looks more finished than it is.
- **Production source would be different.** A real version of this warehouse would land raw data from **Stripe/Chargebee webhooks** (`customer.subscription.updated`, `invoice.paid`, etc.) into a staging area (e.g. S3 + a CDC tool or Stripe's own data export), not a Python generator — the star schema and analytics layer downstream would be structurally the same.

## Methodology deep-dive

**Star schema.** `dim_customer` and `dim_plan` are both **SCD Type 2**, built with window functions (`lead()` over version history to derive `valid_from`/`valid_to`/`is_current`) rather than a `dbt snapshot`. This is a deliberate choice, not a shortcut: `dbt snapshot` is designed to capture attribute changes *as they happen* across repeated pipeline runs over wall-clock time. This project's customer/plan history is fully known upfront (backfilled synthetic history spanning 3.5 years), so the correct way to build SCD2 from it is to derive the version boundaries directly from the ordered history — which is what `dim_customer.sql` and `dim_plan.sql` do.

**MRR waterfall.** `fact_subscription_events` is grain customer × month. For every subscription, `int_subscription_segments` reconstructs a piecewise MRR history (one row per plan the subscription was ever on, with `valid_from`/`valid_to`), and the fact table joins a full month spine against those segments, then classifies each month's MRR delta against the *previous row* (via `lag()`) into `new` / `expansion` / `contraction` / `reactivation` / `churn` / `flat`. One subtlety that actually bit this build: a churned subscription's row sequence would otherwise just *stop* (no explicit $0 row), so `lag()` would never see the drop and churn would be silently undercounted — the model explicitly materializes a $0-MRR marker row for the first calendar month with no coverage after cancellation to fix that. The waterfall view is a `group by month` on top of this fact, and **reconciles exactly**: `prior_month.ending_mrr + this_month.net_new_mrr = this_month.ending_mrr` for every month in the dataset, verified programmatically before this was written.

**Cohort retention.** Cohorts are keyed on signup month from `dim_customer`. The denominator (`cohort_size`) is every customer who signed up that month, **including trial signups that never converted** — this is intentional and matches how retention is usually reported (month-0 retention is honestly below 100% because it includes people who trialed and churned before ever paying).

**NRR.** Trailing-12-month: for every base month, take the MRR held by customers active that month, and compare it to what those *same customers* (zero if churned, whatever they're paying if retained/expanded) are paying 12 months later. New-logo MRR from the intervening year is deliberately excluded, per the standard NRR definition.

**LTV.** Reported two ways per cohort: **observed** net revenue-to-date from actual invoices/payments (honestly low for young cohorts — see Data gaps), and a **formulaic** estimate (`starting ARPU / blended trailing-6-month churn rate`), the standard SaaS approximation. Both are shown side by side rather than picking one and hiding the disagreement.

## Indexing strategy — a measured, not asserted, benchmark

`scripts/benchmark_indexes.py` times (25 runs, median + p95) five real API-shaped queries — point lookups by `customer_id`, a cohort range scan, a filtered join — against a scratch copy of the warehouse, before and after adding B-tree indexes on the natural keys those queries filter on. Actual results from this build:

| Query pattern | Before (median) | After (median) | Speedup |
|---|---|---|---|
| Point lookup: one customer's invoice history | 0.606 ms | 0.229 ms | **2.65x** |
| Range scan: one customer's MRR movement history | 0.278 ms | 0.196 ms | **1.42x** |
| Point lookup: one customer's current dim row | 0.248 ms | 0.248 ms | 1.00x (no change) |
| Range scan: one cohort's retention rows | 0.244 ms | 0.253 ms | 0.96x (no change / noise) |
| Join: invoices × dim_customer, one industry | 1.728 ms | 1.743 ms | 0.99x (no change) |

**Honest read:** indexes help meaningfully (1.4-2.7x) on selective point/range lookups keyed on a table's natural key — exactly the access pattern the per-customer API endpoints would use at larger scale. They do essentially nothing for the cohort/join queries at this data volume, because DuckDB is a **columnar OLAP engine**: it already skips irrelevant row groups via zone maps during a vectorized scan, so a full-table scan over ~24K invoices is already sub-millisecond without an index. This is the correct, general lesson — indexes buy you selective point access, not full analytical scans — and it's why the benchmark reports the negative/flat results instead of only the flattering ones. The live `/api/benchmark` endpoint serves these exact measured numbers (not re-run per-request, since it's a diagnostic over the warehouse, not a live analytics query).

## Why DuckDB instead of Postgres/Snowflake

This is a deliberate zero-infra portfolio choice, not a limitation stumbled into. DuckDB is an embedded, file-based, genuinely columnar SQL engine — it runs real dbt models, real window functions, real indexes, with zero servers to provision and nothing to Dockerize. That keeps the whole project runnable with `pip install` and no external account, while still exercising every SQL/warehouse concept a Postgres or Snowflake warehouse would (star schema, SCD2, incremental load, query tuning). **Production migration path:** swap the `dbt-duckdb` adapter for `dbt-snowflake`/`dbt-postgres` (the model SQL is standard enough to need minimal changes), point `scripts/load_raw_incremental.py`'s upsert at a real `MERGE`/`INSERT ... ON CONFLICT`, and replace the CSV source with a Stripe/Chargebee webhook consumer landing into a staging table — the star schema and analytics layer don't change.

## Setup & run

**Warehouse (optional — a built `warehouse/warehouse.duckdb` is already committed):**

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
python data/seed/generate_seed_data.py       # regenerate data/raw/*.csv (optional, already committed)
bash scripts/run_pipeline.sh                 # incremental load + dbt build (run + test)
python scripts/benchmark_indexes.py          # optional: re-run the indexing benchmark
```

**Backend:**

```bash
cd backend
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
# -> http://127.0.0.1:8000/api/summary, /api/mrr/waterfall, /api/cohorts/retention, /api/nrr, /api/ltv, /api/benchmark
```

**Frontend:**

```bash
cd frontend
npm install
npm run dev
# -> http://localhost:5173  (set VITE_API_BASE if the backend isn't on 127.0.0.1:8000)
```

**CI:** `.github/workflows/nightly_elt.yml` runs the incremental load, `dbt build` (models + all 49 data-quality tests), and the index benchmark on a nightly cron — a real scheduled pipeline, not a decorative badge.

## Limitations & honest TODOs

- Synthetic data throughout — see "Data gaps" above for specifics on what's simplified.
- LTV excludes CAC and gross margin; it's a revenue-retention proxy, not a full unit-economics model.
- The indexing benchmark is measured at this dataset's scale (~24K invoices, ~3K customers); the *relative* finding (point lookups benefit, full scans mostly don't at this size) would need re-validating at 10-100x data volume, where index benefits typically become more pronounced.
- No auth on the API — it's a read-only demo over synthetic data, not a pattern for a real multi-tenant product.
- Cohort heatmap in the UI caps at the most recent 15 cohorts for readability; all 42 cohorts are available from `/api/cohorts/retention` without that cap.
- `usage_monthly` is generated but not yet wired into any analytics view (no usage-based churn-risk scoring) — a natural next feature, not built here.
